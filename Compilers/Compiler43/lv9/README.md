## 一、编译器概述

### 1.1 基本功能

本编译器基本具备如下功能：
1. 解析SysY代码并生成AST
2. 将AST翻译为KoopaIR中间代码。
3. 用翻译出来的KoopaIR生成RISC-V汇编代码

### 1.2 主要特点

本编译器的主要特点是**使用类的继承关系建立AST**、**采用内存形式的KoopaIR**、**采用缓存式的寄存器分配**、**语义分析有一定的错误检测功能**。

## 二、编译器设计

### 2.1 主要模块组成

编译器由3个主要模块组成：词法/语法分析部分负责解析输入的SysY源代码文件，并生成AST；IR生成部分负责将AST生成为内存形式的KoopaIR；目标代码生成部分负责生成RISC-V汇编代码。

### 2.2 主要数据结构

#### BaseAST类

本编译器最核心的数据结构是`BaseAST`，所有其他语法成分的AST均为它的派生类。主要结构如下：  

```c++
class BaseAST {
public:
    virtual ~BaseAST() = default;
    virtual void *toKoopa() const { return nullptr; }
    virtual int calculateExp() const { return 0; }
protected:
    inline static vector<void *> bufferBlocks = {};
    inline static vector<const void *> bufferInsts = {};
    inline static vector<const void *> bufferFuncs = {};
    inline static vector<const void *> bufferGlobalValues = {};
    inline static deque<const void *> stackLoop = {};
    inline static bool insideFunc = false;
    inline static BaseAST::ArrayDecl* decl = new BaseAST::ArrayDecl();
}
```
`toKoopa`函数为最主要的函数，通过koopa.h接口，生成对应不同AST的内存形式IR，返回值一般为`koopa_raw_value_data_t *`，但是也有其他情况，所以采用`void *`作为返回值。

`calculateExp`函数用于在编译时计算常量表达式的值，出于简单起见，本编译器没有更复杂的类派生关系，因此非表达式也具有这一函数，但是正常不会调用。

`bufferInsts`、`bufferBlocks`等buffer用于临时储存指令、基本块、函数。由于接口的实现方式，遇到要加入slice的内容，与其每次都申请一块新内存，不如放入缓冲，再一次性全部复制到slice中。

`stackLoop`是一个两端开口的栈，用于记录当前while循环的起点与终点，用于break与continue的实现。

`insideFunc`标记作用域是否在函数内部，用于判别全局变量与局部变量

`decl`在数组初始化时使用，其数据结构在之后提到。

除此以外，还有一系列静态函数，作为类内部的、使用到AST实际内容的辅助函数，功能包括基本块的管理、左值的获取、初始化lib函数等

出于美观，类中的所有函数分两个文件完成，toKoopa()全部在一个文件中存放，其他所有的函数放在另外一个文件中。

#### SymbolTable类

本编译器的符号表管理主要通过这一数据结构进行，它完全由静态成分组成。主要结构如下：

```c++
class SymbolTable {
public:
    static Item getItem(string ident);
    static Item getItem(string ident, ItemType type);
    static void addItem(string ident, int c);
    static void addItem(string ident, koopa_raw_value_data_t *v);
    static void addItem(string ident, koopa_raw_function_data_t *f);
    static void addTable();
    static void removeTable();
private:
    inline static vector<unordered_map<string, Item> > tables = {};
};
```

`Item`是一个Tagged Union，是符号表的表项，用一个enum来标识存储数据的类型，用一个union来实际存储数据。其中有3个种类，分别是常量、变量与函数。

`tables`是实际存放所有数据的地方，用字符串的ident来区别Item，每一个unordered_map就是一个符号表，用vector存放多个符号表。

函数主要用于操作符号表，包括增删表项、增删表。每进入新的作用域，就增加一个表。具体实现在之后详细说明。

#### ArrayDecl类

`ArrayDecl`是`BaseAST`内部的一个类，专门用于辅助生成数组的IR，尤其是初始化的方面。其结构如下：

```c++
class ArrayDecl {
public:
    koopa_raw_type_kind_t *declType;
    koopa_raw_value_data_t *arr;
    vector<int> dims;
    void *constArrayToKoopa(vector<unique_ptr<BaseAST> > *values);
    void initValuesProcess(const unique_ptr<vector<unique_ptr<BaseAST> > > &values, vector<pair<int, BaseAST *> >& index, int &next);
};
```

`declType`存放数组基本类型。因为类型在Decl中存放而实际初始化是在Def中，所以通过全局成员`decl`中的这一变量来传递。

`arr`是分配数组空间`alloc`指令的地址，相当于数组本身位置所在，其中主要包含数组的type信息，在初始化时必不可少。

`dims`存放数组各维度的长度，并且其本身的长度可以作为数组维数来使用。

`constArrayToKoopa`函数用于常量初始化数组，在全局、常量数组的初始化中使用到。此函数通过递归的方式实现，最终返回一个"aggregate"。

`initValuesProcess`则是变量初始化数组的预处理，此处将多维数组展开成一维数组，`index`参数中按顺序存放数组中不为zeroinit的内容，与它在展开后的数组中存在的位置。

#### 后端

后端主要由一系列`visit`函数的重载组成，加上一些全局变量和辅助函数，用于生成RISC-V汇编代码。严格来说，这一些列函数并没有组织成为一个完整的数据结构，但由于其在后端的重要性相当于`BaseAST`在前端的重要性，故在此列出。

函数中所使用的较重要的全局变量如下所示：
```c++
static unordered_map<void *, string> registers;
static unordered_map<void *, int> used_time;
static bool reg[6] = {false, false, false, false, false, false};
static set<koopa_raw_value_t> spill;
```

`isZero`标记访问的整数是否为0，用于确认是否可以直接使用`x0`寄存器。

`registers`、`used_time`分别存放IR指令与寄存器的对应关系以及IR指令的使用次数，后者用于判断这一指令之后是否会用到，由此确认是否可以释放对应寄存器。

`reg`指示寄存器的使用状况。本编译器除参数以外的大部分寄存器只分配`t0~t5`这六个，`t6`保留作特定作用。`last_reg`记录上一条具有返回值的指令，其返回值所在的寄存器。

`spill`存放需要进行溢出操作的指令，对应指令的返回值寄存器会被溢出。

后端中，自定义了一个`StackFrame`的数据结构，用于模拟实际栈帧的内容，并索引具体内容在栈帧中存放的位置。主要内容如下：

```c++
class StackFrame {
private:
    int currentPos;
    int lastCurrentPos;
    unordered_map<void *, int> stackFrame;
public:
    int length;
    int paramsLength;
}
```

`stackFrame`为主体部分，存放了指令与它相对栈指针的偏移量。

`currentPos`、`lastCurrentPos`分别存放当前栈帧中已经存放到的位置和上一个函数栈帧存放的内容实际存在的位置。在prologue部分将`lastCurrentPos`初始化为上一个函数栈帧的顶部，以便获得栈保存的参数。

`length`、`paramsLength`分别存放当前函数栈帧的总长，以及此函数中调用其他函数时，存放参数所用栈帧的最大长度。

内部还有查找指令与增加指令等相关的函数，在此不多赘述。



### 2.3 主要设计考虑及算法选择

#### 2.3.1 符号表的设计考虑
如前面数据结构中所介绍的，本编译器的符号表主体为`vector`中存放的若干`unordered_map`。其中，一个`unordered_map`就是一个的符号表，多个符号表堆叠起来，自底向上作用域依次缩小，组成一个金字塔型的结构。

首先是全局作用域，在解析`CompUnit`时就加入`vector`中，直到完全结束才退出，从`vector`中删除。之后每进入一个作用域(Block)，就新创建一个符号表加入`vector`中，离开作用域时删除`vector`最后一个元素。如此作用域可以访问上级的符号表，而见不到下级的符号表。

#### 2.3.2 寄存器分配策略
采取以寄存器为缓存的策略。具体做法为：
1. 依次扫描块中指令
2. 有返回值的指令（除`alloc`），记录定义位置和使用的其他指令。对之后不用的指令和当前指令中的非零整数，同时记为定义和使用。调用控制流指令时溢出未使用指令
3. 维护一个`set`，扫描块中指令，将其临时值加入`set`，再检查元素个数，大于6则将`set`中最长寿指令溢出
4. `set`减去指令使用的其他指令集合
5. 若指令有返回值，则加入`set`
6. 重复3~5，直到扫描完毕，若有未使用指令则溢出

#### 2.3.3 采用的优化策略
在短路求值时使用了SSA形式。例如，`x || y`生成为
```koopa
    ...
    %0 = load @x
    br %0, %short(1), %no_short

%short(%result: i32):
    ... //之后的指令

%no_short:
    %1 = load @y
    %2 = ne 0, %1
    jump %short(%2)
```

## 三、编译器实现

### 3.1 各阶段编码细节

#### Lv1. main函数和Lv2. 初试目标代码生成

本阶段主要是对在线文档依葫芦画瓢。开始时由于没写多行注释而交出了第一次的错误。在这一阶段主要熟悉了`.l`和`.y`文件的写法。

#### Lv3. 表达式

这一阶段第一次出现了一个语法成分可以解析成多种不同成分，此时我使用的方法是，对这种成分设置多个不同的AST，如`PrimaryAST1`和`PrimaryAST2`等，不过后期我才意识到可以直接返回下一级成分的返回值，所以多一级结构纯属自找麻烦。

同时，此前我使用字符串形式的IR，在这之后就开始转战内存形式的IR了。

后端方面，由于没有提前看Lv4，所以凭借自己的想象力做了一套简单的寄存器分配。

#### Lv4. 常量和变量

在这一阶段我第一次出现花费了许久才找到的bug。为了找到这个bug，我将整个代码重构了一遍，函数拆分出来，写得更加美观易读了一些。最后找到的bug是有一处`<`和`>`弄反了，令人忍俊不禁。但是这次重构代码也为之后带来了积极的影响。

此外，此时引入JSON库并重写`dump`函数中，用于辅助debug。

还有，后端本来在文档的建议下，写成了全部存在栈上的寄存器分配形式，但是测评时出了AE，改回之前的寄存器分配反而AC了，于是就把这一套寄存器分配策略一直沿用，直到Lv8和Lv9分别大改一次。

#### Lv5. 语句块和作用域

这一阶段算是整个过程中最简单的部分了，不过也犯了一些小错误，比如当`Block`中没有东西时，退出作用域忘记删除符号表了。除此以外，一切顺利。

#### Lv6. if语句

二义性的问题其实反而没什么好说的，毕竟去wiki上查一查，解决方案直接就写在里面了，而且文档里面把wiki的链接都摆好了，再不会就对不起wiki作者了。

这一阶段最麻烦的还是块之间的跳转，基本块结尾必须是`jump`、`br`、`ret`之一，这个要求导致我反复修改了许久。另外，例如`if...else...`后面没有其他语句导致的空块也令我烦恼了一段时间。

在这一阶段，我进一步重构了代码，将`toKoopa`完全统一为一个函数，不再有各种传不同参数调用不同重载的情况。另外，这也是我在Lv3中所提到的，简化语法分析和AST树的时期。

同时，写这一阶段的时候刚好遇到课上讲了SSA形式，所有我就直接在短路求值里面用到了。后端处理块参数的时候有些麻烦，不过最后还是克服了——反正块参数只有这里用了，也不会超过8个，所以大致写对了就直接过了。

#### Lv7. while语句

这一阶段和Lv5相比是另一个意义上的简单，基本上只要Lv6写对了，Lv7就完全没有任何问题。但是不出意外地，还是出意外了。依然是空块的问题，Lv6的时候没有测出来的问题在Lv7暴露出来了。不过好在debug用时不算长。

#### Lv8. 函数和全局变量

前端在这一阶段还是挺简单的，但是后端的难度就直线上升了。在这一阶段，第一次出现了一次性使用超过2个变量的语句，之前那一套简单的寄存器分配策略在这里就行不通了，于是连夜查找寄存器分配的相关文献，本来想写LSRA的，但是觉得太麻烦了写不来，所以修改之后写成了现在的这种形式。最开始写的时候有一堆漏洞，还好在各种WA和CTE的轰炸之下，缝补得凑合能看。

传参其实没什么好说的，毕竟我用到的寄存器是`t0~t5`，和`a0~a7`没啥关系，而且有之前块参数的经验，所以没花多少功夫就写完了。至于超出8个的返回值，稍微想了想办法，在`StackFrame`上动了点脑筋，就找出了解决办法。

返回值？那是什么？没啥印象了，可能不算难，也可能被寄存器分配弄失忆了吧。

#### Lv9. 数组

不得不说，多维数组初始化，就是地狱。

常量初始化的时候，因为要返回aggregate，所以类型的对齐就成了一个难点。在这里，写内存形式真不如写字符串形式，我花了九牛二虎之力，在GDB上盯着看了一晚上才看明白它的结构到底长什么样，又花了一个晚上来想办法解决怎么构造这种aggregate的问题。最后在近乎炼丹的尝试下，终于调出了正确的aggregate，尝试了至少8个小时。

而变量初始化的时候，按正常写法，每到新维度就要重新做`getelemptr`，实在太麻烦了，所以我采用了一个比较dirty的方法，就是直接获取数组首个元素的地址，然后用预处理的方法将多维数组展开成一维数组，再用一维数组的方式去储存初始化列表里的元素——反正变量初始化的时候都是要一个一个存，这和一维数组有什么本质区别？而预处理则是使用了和常量类似的递归方法。

就这样，多维数组初始化的问题终于解决了。接下来赶到的是，数组参数。由于数组参数使用的`getptr`与之前使用的`getelemptr`好像差不多一回事，又好像不是一回事，所以我反反复复弄了老半天才弄明白这玩意到底是干什么的。弄清楚了之后，说难也不算难，对着样例修修bug，莫名其妙就过了。

至于后端，由于我前面的写法还是有偷懒，所以在这里遭报应了。之前，由于基本上都是后来的寄存器先用，我只需要记录寄存器使用的个数，要新的寄存器直接数量++就行了，但是碰到`getelemptr`似乎就行不通了，计算偏移量时，有时一条语句会被多次使用，它所在的寄存器没法释放，于是跟着它之前的寄存器也相当于被占用了，所以最后改成了现在的这种写法。修改的过程也是极其痛苦的，改来改去本来应该对了的Lv8都出错了。最后在看汇编看得眼花之后，终于改对了。

在进入这一阶段后，样例变得刁难许多，所以之前很多能凑活的漏洞在这一阶段一下子全部暴露了出来，所以又不得不查漏补缺，像是之前对`used_by.len == 0`这种情况，只对`binary`操作有考虑，但是实际上只要有返回值就应当考虑，但是之前却没发现。不过最后总归是写对了，也取得了一个比较满意的性能。

### 3.2 工具软件介绍
1. `flex/bison`：用于词法/语法分析，将输入的SysY代码解析为语法树，并建立AST
2. `libkoopa`：为构建内存形式的KoopaIR提供了接口，定义了构建内存形式KoopaIR相关的一系列数据结构，并且提供了将内存形式与字符串形式相互转化的能力。
3. `jsoncpp`：用于输出AST的结构，辅助debug。

### 3.3 测试情况说明

#### Lv4
构造了一个用例，使用了所有的运算符号，并对变量和常量分别尝试，终于定位出在符号标反的问题。

#### Lv5
构造了一个用例，其中包含大量嵌套的空的`Block`，然后发现退出时`vector`的元素个数异常，最终发现问题。

#### Lv8
构造有不同参数个数的函数，观察生成代码的表现，并一点点找到逻辑问题。还有与之前的代码进行对比，观察寄存器分配策略重写后有无疏漏之处。以及通过各种不同数量的不同指令组合来观察溢出情况，通过这种方法我就发现call之前未使用的指令没有溢出导致了bug。

#### Lv9
通过与`Compile Explorer`生成的代码进行比较，得出了正确的多维数组初始化方法。通过运行之前的测试用例，发现重构代码带来的问题。以及使用往年用例调试等等。

### 4.2 学习过程中的难点，以及对实习过程和内容的建议
1. 难点集中在Lv6、Lv8、Lv9，其中难度又逐步上升。最主要的是，有大量的细节必须保证不出问题，这就导致对精神的损耗非常大。而前期虽然不能说简单，但也决谈不上难，和后期的难度、工作量不是一个量级的，曲线陡增。特别是碰上期末，时间不多，雪上加霜。
